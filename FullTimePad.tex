\begin{abstract}
	Essential properties in ciphers include computational efficiency, security, and economical feasibility. Encryption scheme based on one-time-pad (OTP) is secure, but there are two security risks: (1) a key cannot be reused and (2) plaintext length equals the key length which is costly \& inefficient for long plaintexts. As stated by Claude Shannon, father of information theory \cite{shannon1945}, a secure cryptographic algorithm requires both confusion and diffusion. However OTP lacks the confusion and diffusion per ciphertext.
	In this study, we proposed the \textbf{full-time-pad (FTP)}, a symmetric stream cipher that extends OTP by incorporating both diffusion and confusion.
	% In this study, we proposed the \textbf{full-time-pad (FTP)} which is a symmetric stream cipher that extends OTP by incorporating both diffusion and confusion.
	To achieve diffusion, symmetric key is permutated in its byte form using a constant permutation matrix. The permutation ensures that every 32-bit number is derived from different bytes of the key.
	Using modern hardware optimizations (Vectorization, Cache and Parallelization, this operation is computationally efficient.
	To achieve confusion, the key is manipulated in 32-bit segments using Modular \textbf{A}ddition, Bitwise \textbf{R}otations, and \textbf{X}or (\textbf{ARX}).

\end{abstract}

\section{Introduction}

Fast \& efficient encryption algorithms are a desired concept for both large and small amounts of data. Single Instruction Multiple Data (SIMD) instructions in modern devices are a golden opportunity for hardware optimized cryptographic algorithms. Even though newer algorithms like Blake-3 utilize it, their benefits aren't maximized. According to benchmark tests on FTP, most cache misses happen in the first round of permutation, next permutations are consistently faster which is why using multiple permutations are a worthwhile approach. FTP is three times faster than ChaCha20 because it is built for modern hardware. SIMD Parallelization has been around since 1962 \cite{sung_mit_2000}, yet they have been popularized since the early 1990s \cite{wiki_simd}. SIMD exists in nearly all modern devices and we present that cryptography should adapt to this modernization. One of the main reasons why multiple rounds of permutations aren't considered in previous works is because diffusion relied on transposing bytes located in RAM while FTP relies on cache and SIMD optimizations.
In the Efficient Permutation Instructions for Fast Software Cryptography \cite{palms_princeton_2001} publication from Princeton University, bit-level permutation optimization are introduced. Such algorithms would significantly reduce the number of rounds needed for a cryptographic algorithm such as ChaCha20 which includes 20 rounds of transformations yet FTP only requires 10 rounds. This is because of the byte-level permutation mixed with simple ARX operations. However, hardware bit-level permutation optimizations aren't offered in personal devices as of now, and should only be considered for future algorithms.

\section{Security}
\setlength{\mathindent}{3pt} % No indentation for equations

In OTP, key cannot be reused. This is demonstrated by the following:

\[
\begin{aligned}
&\texttt{let }  m_1, m_2 \texttt{ be 2 plaintexts} \\
&\texttt{let }  k \texttt{ be the key} \\
&\texttt{let }  c_1 = m_1 \oplus k \\
&\texttt{let }  c_2 = m_2 \oplus k \\
&c_1 \oplus c_2 = (m_1 \oplus k) \oplus (m_2 \oplus k) \\
&c_1 \oplus c_2 = m_1 \oplus m_2
\end{aligned}
\]

Since the key is reused, the 2 ciphertext's XORed factor out the key since $k \oplus k = 0$
Using cryptoanalysis, the 2 plaintexts can be found as demonstrated by OneTimePad Cracker on GitHub by Kibnakamoto. 
\\
To imply that $c_1 \oplus c_2 \neq m_1 \oplus m_2$ implicitly requires that the key is updated per encryption. If $k$ is transformed each time so that it has an avalanche effect. Even with no confusion, it would still be secure since $k' \oplus k \neq  0$ where $k'$ is transformed key. 
\\
But there is another concern,
\\
If the plaintext and ciphertext are known (known plaintext attack), then it is possible to find $k$ so avoid using k without transformation since $\texttt{plaintext} \oplus \texttt{ciphertext} = \texttt{key}$, for each plaintext, key needs to be transformed irreversibly and also requires confusion since if $k'$ is found, $k$ is still unknown but if $k$ is found, then all instances of $k'_n$ are known, which means that: 
\[
\begin{aligned}
&k'_1 = hash(k+1) \texttt{ where hash() is an irreversible transformation} \\
&k'_2 = hash(k+2) \\
&c_1 \oplus c_2 = (m_1 \oplus k'_1) \oplus (m_2 \oplus k'_2) \\
&c_1 \oplus c_2 \neq m_1 \oplus m_2 \\
&m_1 \oplus c_1 = k'_1 \\
&m_2 \oplus c_2 = k'_2 \\
&k'_1, k'_2 \texttt{  are calculated using an irreversible hashing algorithm }
\end{aligned}
\]
\\


$\therefore$ \texttt{FTP} requires both diffusion and confusion

\subsubsection {Collision Attack} \label{collision_attack}

Most Denial of Service (DOS) attacks related to encryption algorithms are based on brute-force methods. Following is the proof that there are no potential collision attack vulnerabilities in the form: \\
$\texttt{transform(} key_1 \texttt{)} = \texttt{transform(} key_2 \texttt{)}$ \\
\\
Addition can be observed as an encryption algorithm. For example: $x + y = 16$ \\

$ x,y \in \mathbb{Z}, 0 \leq x,y < 256$ \\
there are 17-combinations for x to satisfy this expression, and simultaniously, there are 17 combinations for y to satisfy the expression, so there is a total of $17$ combinations.
\\
But for $x + y = z$, there are $256$ combinations to try. if the result of an arithmetic operation is known, there may be ways to get the same end-result with less combinations to brute-force. Knowing the value of $z$ reduced the number of combinations by $15$ times.

$\therefore$ if there is an operation that can provide the same output for a wide range of inputs, there can be a collision attack. Collision attacks can be used to derive the same transformed key using a different input key and decrypt the plaintext without actually having the original key.
\\
In the context of this encryption algorithm (using addition as an example operation): keysize is 32-bytes
\\
so for each byte n: $x_n + y_n = z_n$\\
$ x,y,z \in \mathbb{Z}, 0 \leq x,y,z < 256$\\
\\
Number of combinations can be represented by 
\[
\\		\prod_{n=0}^{32-1}(z_n+1)
\]
\small so the number of combinations would be between a minimum of 32 combinations ($z_n=0$ for all 32-bytes) up to a maximum of $2^{256}$ combinations ($z_n = 255$ for all 32-bytes) which can be brute forced for small $z_n$. So a simple addition is prone to collision attacks for $x_n+y_n=z_n$, where $x,y$ are unknown.
\[
\\\sum_{i=0}^{z_n} x_i + y_i \equiv z_n \Longrightarrow
\sum_{i=0}^{z_n} (z_n-i)+(i) = z_n
\]

Solves for all possible $x, y$ values for each $z_n$. An addition operation can be represented differently to solve for 2 unknowns, while a good mix of ARX operations cannot be reverse engineered. Addition of encryption index + key might lead to vulnerabilities. Also pre-manipulation of key to other values such as a constant would be infeasible because it would provide no further security benefits.

Therefore the alternative final secure solution is to calculate sum of each 32-bit segment of the key (represented by $k_i$) in order to interlink them to make sure that every byte of the key offers the same avalanche effect:
\[
\\\sum_{i=0}^{7} k_i
\]

To stress test if this concept offers enough collision resistance: think of this problem as an example:
\\
\textbf{1.} $x+y=16 \texttt{\hspace{2.3cm} offers n=17 combinations}$\\
\textbf{2.} $x+y+z=16 \texttt{\hspace{1.7cm} offers n=153 combinations (determined experimentally)}$\\
\textbf{3.} $x+y+z+v=16 \texttt{\hspace{1cm} offers n=969 combinations (determined experimentally)}$\\
$x,y,z,v \in \mathbb{Z}, 0 \leq x,y,z,v < 256$\\

So there has to be an equation or algorithm to summarize the relationship between number of variables ($\ell$) and the sum of the addition operation ($16$);

Knowing that equation \textbf{1.} is the simplest equation and it offers 17 combinations. Then if the rest of the equations are represented in 2-variable fashion. we can find number of combinations $n$:

For equation \textbf{2.}: There are 3 ways to represent as 2-variable equation

The number of ways a multi-variable equation can be represented as a 2 variable equation can be summarized by the following:

\[
\\ \sum_{i=1}^{\ell-1} i
\]

Using some number crunching and logic, we found that there is a direct corrolation between the number of combinations and the ratio between the current number of ways to represent as 2-variable equation over the previous number of ways to represent as a 2-variable equation:

\[
		\\ n_\ell \approx \propto \frac{\displaystyle \sum_{i=1}^{\ell-1}}{\displaystyle \sum_{i=1}^{\ell-2}} \times k \hspace{1cm} \texttt{where k is a multiplier:} k \in \mathbb{N} 
\]

Using more number crunching: We found the following recursive formula that finds the number of combinations that satisfies x+y+\dots = 16:

\[
		\\ n_\ell = (n_{\ell-1} \frac{\displaystyle \sum_{i=1}^{x}}{\displaystyle \sum_{i=1}^{x-1}} +17) \times 3 - 17 \times 3( (x+1) \mod 2 )
\]
where $x = \ell-1$ \quad and x should be incremented until correct answer is reached for $\ell \geq 6$ and $n_{\ell-1}$ is previous number of combinations.
This formula doesn't translate to cases where the 2-variable equation doesn't have 17 combinations.

Simply put this equation couldn't be used accurately, it can only be an approximation. But upon further number crunching, we derived the following formula that satisfies all cases:

\[
\\ \prod_{i=0}^{\ell-1} \frac{(x+i)}{1+i}
\]
\\

where x is the number of combinations for 2 variable equations. e.g. for $a+b = 16, x = 16+1 = 17$.

Which leads to the following equation. The equation contains a costly operation (factorials) so it is computationally slower, but for approximation of really large numbers (e.g. sum of billions of variables), this is preferred as it is hard/unnecessary to calculate the exact answer using the formula when $\ell$ or $c$ is unrealistically large:

\[
\\ \frac{(\ell+c)!}{c!\ell!}
\]
\\

Using the Ramanujan Approximation:

\[
\\ n! \approx \sqrt{\pi}\left(\frac{n}{e}\right)^n\sqrt[6]{8n^3 + 4n^2 + n + \frac{1}{30}}
\]

The following approximation equation can be derived for really large calculations:

\subsection{Time Based Attacks}

Time based vulnerabilities are exploited by the deduction of numbers present in the algorithm from computation benchmarks. Time based attacks are used to find a side-channel vulnerability (hardware/software) where the attacker approximates the value of the key by timing the calculation speed.
\\
Arithmetic operations such as multiplication contains vulnerabilities since multiplication not a constant time operation. But arithmetic such as ARX operations are always constant time which is why the selected confusion/diffusion operations are chosen.

Experimentally, we can evaluate the possibilitiy of time-based vulnerabilities using the following algorithm:
Start from 32 zeros for a key, then incremented each byte by 1 until there are 32 255s and test again. 
\\
\texttt{----------TESTING SIDE CHANNEL ATTACKS----------\\
TESTING TRANSFORMATION VERSION 1.0: PASSED (NO SIDE CHANNEL): data is consistent\\
TESTING TRANSFORMATION VERSION 1.1: PASSED (NO SIDE CHANNEL): data is consistent\\
TESTING TRANSFORMATION VERSION 2.0: PASSED (NO SIDE CHANNEL): data is consistent}\\

This algorithm is implemented in \texttt{test/benchmark.cpp} in the function \texttt{benchmark\_hash\_time\_attack\_v()}. This test passed, which was never in doubt. The keys with small numbers have the same speed as keys with large numbers, therefore algorithm is proven to be constant time.

Tested for time-based side-channel attacks by comparing the computation time for different key values, If computation time for smaller key (32 0s) approximately equals to computation time for (32 255s) key, then data is consistent.

\subsection{Linear Cryptoanalysis} \label{lin}

Linear Cryptoanalysis is used to find linear connections between ciphertexts and plaintexts. Linear differences in algorithms are easily exploitable weakness. Linear operations in this algorithm are byte-permutations, bitwise rotations, and xor which overall bring a strong diffusion. But not sufficient for confusion. So using addition in the ring $\mathbb{Z}_{2^{32}}$ is necessary to pass linearity tests due to carries. It's important to note that prime galois field addition is considered linear under $\mathbb{F_p}$ and do not bring  non-linearity.
\\
Initially, using linear algebra definition of a linear transformation, this algorithm is proven to be non-linear since $\texttt{transform}(c_1k_1 + c_2k_2) \neq c_1\texttt{transform}(k_1) + c_2\texttt{transform}(k_2)$. This doens't mean that they lack correlation with probabilities, so further statistical analysis is required.

In order to find linear patterns with statistical analysis, using well-known proven algorithms is a solid approach.

One linear pattern is how many outputs bits flip per input bit flip. This test is known as the Strict Avalanche Critirion (SAC). SAC test passed with a 50\% chance of bit flip for every output bit for each input bit.

SAC can be further analyzed by checking indipendence of output bit flips using the Bit Indipendence Critirion (BIC) test. This test passed successfully and the xor of each 2 output bits follows a non-linear random pattern.

\subsubsection{Constant - $r$ - Dynamic Rotation Constant} \label{rotation_constant}

Cicadas only surface once every 17 years. Assuming their predetor only surfaces once every 2 years, they will only meet each other once every 34 years. Since 17 is a prime number, they will barely ever meet. However, if they surfaced once every 18 years, while their predetor once every 2 years. Then every 18 years they would meet. This would also make it easier for the predetor to synchronize their emergence timing.\\
let x be the time interval for when the cicadas surface \\
let y be the time interval for when the predetors surface \\
We can deduce:\\
$GCD(x,y) = 1$, then they meet up every $x \times y$ years. \\
Whereas if $GCD(x,y) \neq 1$, then they meet up every $x$ years (assuming $x > y$). \\
\\
Bitwise rotation operation should also be done with either a prime number or a number where $GCD(x,y) = 1$ to maximize the collision resistance.\\

Here is a counterexample as proof \\
let $w$ be 32-bit number\\
let $q = 8$ be rotation count\\
rotation can be represented by: $w = w \lll q$\\
If this rotation was repeated for 4 iterations, then the rotations would cancel out and rotated $w$ ($w'$) and $w$ would be equal. Make sure that $GCD(q, 32) = 1$. \\

If there's only one rotation number, the likelihood of finding a pattern increases. Using a single rotation number is not sufficient, but if the bits were shuffled using a more complex method, the process becomes harder to reverse. Even though each method is reversible on its own, combining them makes it significantly more difficult to undo. The use of bitwise rotations on 32-bit segments combined with byte-level permutations creates excellent diffusion.

Rotation numbers that were selected is represented by r:

\[
r = 
\begin{pmatrix}
		23 & 5 & 17 & 31 & 13
\end{pmatrix}
\]

There are 5 numbers in r, this is because $16 \mod 5 \neq 0$, after 16 iterations in the transformation algorithm, all values of k aren't rotated the same number of times.

if a 32-bit unsigned integer (x) is rotated by r
\[
\sum_{i=0}^4 r_i = 89
\]
\\
The total rotation is 89 (prime). $x \ggg 89$ would produce a net rotation of $x \ggg 25$, since $89 \mod 32=25$. Knowing that $GCD(25, 32) = 1$, the minimum number of times where the expression $x \ggg 89$ is repeated until $x \ggg 89 = x$ is $32$ times since $GCD(25 \times 32, 32) = 32$. Considering that there are other operations than bit shifts, the total bit rotation (89) reflects the transformation of bits better than the net rotation (25).
%This means that only after $2848$ iterations would rotated x equal x. Whereas if there was a singular number for $r$, the number of rotations for rotated $x$ to equal $x$ would be $r \times 32$ (e.g. $r=23, 23 \times 32 = 736$). \\

$\therefore$ r must contain multiple numbers.
\\
FTP is designed so that $|r_i - r_{i-1}|$ results in a different magnitude for all elements of r so that diffusion from bitwise rotations are maximized.
\\
Derivation of r is as follows: make a set (r) of all prime numbers from 0-32, remove elements based on similiarity of results of $|r_i - r_{i-1}|$ (e.g. $23-5=18$, $|5-17|=12$). A good net rotation would be prime. FTP consists of both bitwise right rotate ($\ggg$) and bitwise left rotate ($\lll$), in order to properly mix the results.

\section{Hashing}

The 'hashing' algorithm is used for manipulating the key per plaintext with proper confusion and avalanche effect. The main reason why the key can be reused is due to the algorithm's strong avalanche effect as well as the lack of statistical patterns.
\\
To maximize the effects of confusion in FTP, half of the key is modified per iteration. Every byte of the key is transformed a total of 8 times ($\frac{16 \texttt{iterations}}{8 \div 4}$). FTP 1.0 \& 1.1 consists of 16 iterations and since $16 \mod 2 = 0$, all bytes are transformed the same number of times which would lower the possibility of a statistical exploit that could target less transformed bytes of the key.
\\
Half of the key should be modified per iteration because classical cryptographic algorithms (non-quantum) rely on computational complexity for their security. So more transformations the better. Although the minimum work to get a secure transformed key is enough, \\
it's often preferred to have extra insurance rounds for further security at the expense of computation speed.
\\

	\State $ \mathrm{sum} \gets \displaystyle \sum_{j=0}^8 k_j$

	\State $A_\mathrm{imod9} \gets A_\mathrm{imod9} \oplus \mathrm{sum}$

	\State $k_\mathrm{i2mod} \gets k_\mathrm{i2mod} + A_\mathrm{imod9} + k_\mathrm{i2mod} \lll r_\mathrm{rmod}$
	\State $A_\mathrm{imod8} \gets A_\mathrm{imod8} \oplus k_\mathrm{i2mod}$

	\State $k_\mathrm{i3mod} \gets A_\mathrm{imod8} \oplus k_\mathrm{i3mod}$
	\State $k_\mathrm{i4mod} \gets A_\mathrm{imod8} \oplus k_\mathrm{i4mod}$ \\

	\COMMENT{Permutate the bytearray key}
	\State \texttt{key} $\gets$ dynamic\_permutation(\texttt{key}, i);
\EndFor
\State increment \texttt{encryption\_index} by 1 for each plaintext
\State \textbf{Return} $\texttt{key}$
\end{algorithmic}
\end{algorithm}

\subsection{Transformation - Version 2.0 - Prioritize Speed}

This version of the transformation prioritizes speed. FTP 2.0 is preferred to FTP 1.1 for cases where complexity isn't the primary focus. This is still considered secure, but lacks the extra complexity found in FTP 1.0. FTP is designed to offer less rounds, and less bytes modified per round, but heavier manipulation per round.

\subsection {Key Reuse}

A 64-bit nonce labeled an encryption index is used for key reusability. The difference between a nonce and encryption index is that an encryption index cannot be random. if a random nonce was used instead, this could lead to collisions since root $k$ for $g(2^{64}, k) = 5,056,937,540$ where $g$ is the solution to the birthday problem defined in section \ref{birthday_problem}. This means that there is
a 50\% chance of collision when 5 billion 64-bit nonces are used.
161,822,001,280 bytes of data would need to be encrypted for a succesful brute-force to be 50\% likely. In practice, using random nonces would increase chances of collisions
significantly. Safest practice is to increment the encryption index.
\\The first 2 values of A is the encryption index. Encryption index must be located in the first half of A to provide more iterations to diffuse in the encryption index.

\subsubsection {Multi-Threading}

When multiple threads are encrypting using the same key, the encryption index needs to be an atomic variable. If using an atomic number isn't possible (e.g. threads cannot communicate efficiently), then use one the following methods:

\begin{algorithm}[H] % H is to make the algorithm stay HERE
\caption{Unique nonces for Multi-threading without thread communication}
\label{thread_nonce}
\begin{algorithmic}[1]  % The [1] enables line numbering
\State \textbf{Input:} thread count ($t$), thread ID ($n$)
\If {first \texttt{encryption\_index}}
    \State $\texttt{encryption\_index} = n$
\Else
    \State Add $t$ to \texttt{encryption\_index}
\EndIf
\State \textbf{Output:} Nonce (\texttt{encryption\_index})
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[H] % H is to make the algorithm stay HERE
\caption{Unique nonces for Multi-threading without thread communication}
\label{nonce_unique}
\begin{algorithmic}[1]  % The [1] enables line numbering
\State \textbf{Input:} thread count ($t$), thread ID ($n$), last encryption index used on this thread ($m$), $m > 0$, ordered set of $t$ prime numbers ($P$)
\State let $\texttt{encryption\_index} \gets n + m + 1$
\State let $p \in P, p \neq P_n$
\While { $\gcd(\texttt{encryption\_index}, p) > 1$ }
    \State $\texttt{encryption\_index} += P_n$
\EndWhile
\State \textbf{Output:} Nonce (\texttt{encryption\_index})
\end{algorithmic}
\end{algorithm}

These algorithm are only valid if number of threads used is not growing. Otherwise, every time a new thread is created, the algorithm needs to be recalled with a new $t$. If thread count is not constant, set thread count to maximum possible number before executing the algorithm.

Algorithm-\hspace{0.1em}\protect\ref{nonce_unique} is inefficient and slow so it should be avoided in practice.
$\therefore $ Use \textbf{Algorithm \hspace{0.1em}\protect\ref{thread_nonce}} for generating incremental nonces without thread communication.

When encrypting long plaintexts, using encryption modes such as Galois Counter Mode (GCM) is always the best option but it is also secure to increment the encryption index per 32-byte plaintext block.

\subsection {Encryption/Decryption operation}

Encryption operation is the same as decryption

\begin{algorithm}[H] % H is to make the algorithm stay HERE
\caption{Encrypt/Decrypt transform Function}
\begin{algorithmic}[1]  % The [1] enables line numbering
\State \textbf{Input:} plaintext ($p$), length ($\ell$), 32-byte original key ($k$), encryption index/nonce (\texttt{encryption\_index})
\State \textbf{Output:} ciphertext ($c$)
\For {each 32-byte segment of plaintext}
	\COMMENT{create a copy of unmodified $k$, and transform it using an incrementing unique \texttt{encryption\_index}}
	\COMMENT{Then, encrypt using plaintext xor transformed key = ciphertext}
	\State copy = copy($k$)
	\State $c \gets c \,||\, p \oplus \mathrm{transformation(copy, } \texttt{  encryption\_index})$
\EndFor\\
\\
\COMMENT{For the remainder:}
\State $c \gets c \,||\, p \oplus \mathrm{transformation(copy, } \texttt{  encryption\_index})$
\State \textbf{Return} $c$
\end{algorithmic}
\end{algorithm}
